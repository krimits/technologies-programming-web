# SPEC — ΕΡγασία 1 (ακριβής προδιαγραφή, τα «κρυφά» σημεία)

Αυτό το αρχείο είναι **ανάφοση** (αποσπάσματα από το κείμενο της εργασίας + ερμηνεία).
Δεν είναι λύση: υλοποίηση, ονοματολογία και σχεδιασμός δικά σου.

## 1. Μοντέλο δεδομένων

Χρήστης (Θέμα Α) — από τη φόρμα:

| Πεδίο | Τύπος | Σημειώσεις |
|---|---|---|
| firstName | string | κεφαλαία ελληνικά, χωρίς τόνους, υποχρεωτικό |
| lastName | string | ίδια κανόνικα |
| email | string | format + **μοναδικό στο σύνολο** |
| role | `'Admin' \| 'User'` | τιμή από select/radio |
| registrationDate | string (ISO date) | σημερινή ημερομηνία, readonly |
| password | string | κανόνες πολυπλοκότητας, **μόνο localStorage (εκπαιδευτικό)** |

Θέμα Β (Mini e-shop) — προϊόν: `name`, `category`, `price` (number), `available` (bool).
Τα προϊόντα αποθηκεύονται στο ίδιο pattern (πίνακας → `JSON.stringify` → `localStorage` key `products`).

## 2. Κανόνες επικύρωσης (ακριβείς, με παραδείγματα)

### Email
- Έγκυρο μορφής: κάτι σαν `name@domain.tld` (η μορφή του browser `type="email"` είναι αρκετή για το «format»).
- Μοναδικό: δεν υπάρχει ήδη στους αποθηκευμένους χρήστες. Η σύγκριση case-insensitive είναι ασφαλέστερη επιλογή
  (αλλάξε το πρώτο γράμμα σε πεζό και το ίδιο email πρέπει να θεωρείται duplicate).
- Το ίδιο ισχύει και στην Εργασία 2, εκεί ως **unique index** στο schema.

### Όνομα / Επώνυμο
- Επιτρεπτά: `Α`–`Ω` (U+0391–U+03A9), χωρίς τόνους/διαλυτικά.
- Απαγορευμένα: πεζά ελληνικά, τόνια/διαλυτικά (`Ά Έ Ή Ί Ό Ύ Ώ Ϊ Ϋ`), λατινικά, ψηφία, σύμβολα.
- Επιτρέπεται: κενό **ή** παύλα ως σύνδεσμος σύνθετου ονόματος → `ΑΝΝΑ-ΜΑΡΙΑ` ή `ΑΝΝΑ ΜΑΡΙΑ`.
- Πρακτικά: ένα regex που δέχεται `Α-Ω` και επιτρέπει `-`/κενό ανάμεσα σε ομάδες κεφαλαίων.
  Λάβε υπόψη ότι το `[Α-Ω]` σε JS **περιλαμβάνει** τα `Ϊ`/`Ϋ` (U+03AA/AB) → πρέπει να τα εξαιρέσεις
  (π.χ. αρνητικό lookahead ή explicit range) — αυτό είναι το κλασικό «κρυφό» σημείο της εργασίας.
- Άλλο πόλιμα: τα `^`/`$` της JS αντιστοιχούν σε string boundaries, όχι σε γραμμές →
  χρησιμοποίησε `\p{L}`/anchors σωστά ώστε να μην περνάει το `ΓΕΩΡΓΙΟΣ\n` (strip newlines ή χρήση `$` + `\s*`).

### Password
- ≥ 8 χαρακτήρες
- ≥ 1 γράμμα
- ≥ 1 αριθμός
- ≥ 1 από `!@#$%^&*` (ακριβώς αυτά τα 8 σύμβολα)
- Έγκυρο παράδειγμα: `123A$6789` · Μη έγκυρα: `Abcdefg1`, `12345678$`, `Ab1$`
- Το `minlength` του HTML δεν καλύπτει «να έχει γράμμα/ψηφίο/σύμβολο» → δικό σου validator.
- Ένδειξη `✔/✘` **ανά κανόνα** (μήκος / ψηφίο / γράμμα / σύμβολο) — 4 ενδείξεις, όχι μία.

### Confirm password
- Πρέπει να ταιριάζει με το password σε κάθε αλλαγή, και να μην μένει «γκριζοποιημένο» μετά από άδειο password.

## 3. Live validation — πότε ενημερώνεται

- Trigger: `input` event (όχι μόνο `change`/`submit`) → «Σε κάθε πεδίο εμφανίζεται άμεσα».
- Μην κάνεις `form.checkValidity()` στο submit και σταματάς εκεί — το live feedback είναι το ζητούμενο.
- Μην κάνεις `reportValidity()` σε κάθε keystroke: συχνά «κρέμει» τον browser και δεν σου δίνει έλεγχο
  του μηνύματος. Δικό σου μήνυμα + `setCustomValidity` όταν θέλεις να αλλάξεις το native bubble.
- Ένα input που έχει γίνει touched (ο χρήστης το πλήκτρολόγησε/το άφησε) δείχνει error,
  αλλιώς μην εμφανίζεις error σε άδειο πεδίο (ειδικά «Έγκυρο» σε άδειο πεδίο είναι ψευδαίσθημα).

## 4. Υπολογισμός «Έγκυρο»

Σκεψεί το ως δύο ξεχωριστά πράγματα:
1. **Έγκυρο/μη έγκυρο για το πεδίο** (το κρίσιμο για τη βαθμολογία).
2. **Μη ενεργοποιημένο submit** όσο η φόρμα δεν είναι έγκυρη (απλό UX, δεν βαθμολογείται ρητά αλλά ενισχύει το «UX 5%»).

## 5. Αποθήκευση

- `localStorage` key: **`users`** (ή `products` για το Θέμα Β) — ακριβώς όπως στο κείμενο.
- Write: `JSON.stringify(array)` σε κάθε add/edit/delete (όχι «μια φορά στο τέλος»).
- Read: `JSON.parse` κατά το load της σελίδας, με ασφαλή fallback αν το JSON είναι χαλασμένο.
- Όλα τα reads/writes να περνούν από το `UserStore` (μία πηγή αλήθειας) — όχι `localStorage` από τα events.
- Το password αποθηκεύεται **σε plaintext** στο `localStorage` (αποδεκτό για την άσκηση) —
  αλλά **πρέπει** να το αναφέρεις στο README (η εργασία το ζητά ρητά).

## 6. Πίνακας, ταξινόμηση, φίλτρο

- Edit: δεν δημιουργεί νέο χρήστη — ενημερώνει τον υπάρχοντα (ίδιο id) και **ελέγχει ξανά uniqueness**
  του email (αλλάζεις το email σε ήδη υπάρχον).
- Delete: `confirm()` ή custom modal (το custom είναι πιο «ποιοτικό» για το UX).
- Sort: αύξουσα/φθίνουσα ανά στήλη, με toggle και οπτικό δείκτη (↑/↓).
- Search: case-insensitive, ταυτόχρονα σε firstName + lastName + email.
- Filter: ρόλος Όλοι/Admin/User.
- Κενό αποτέλεσμα → «Δεν βρέθηκαν χρήστες» (και όχι απλώς κενός πίνακας).
- Το `render()` να αλλάζει μόνο το tbody (μην ξαναφτιάχνεις όλο το DOM σε κάθε keystroke — χάνεται focus).

## 7. Bonus details

- **Export**: CSV (με escaping σε quotes/commas) ή JSON download (Blob + object URL).
- **Import**: file input → parse → επικύρωση κάθε εγγραφής **με τους ίδιους κανόνες της φόρμας** →
  απόρριψη duplicates (επιβεβαίωση/επισήμανση) → ενημέρωση του store → ενημέρωση του πίνακα.
- **Pagination**: σελίδα = 10 χρήστες· το «δείξε όλους» ή το filter αλλάζει σύνολο σελίδων.
  Πρόσεξη: το page index πρέπει να μηδενίζεται/περιορίζεται όταν αλλάζει το αποτέλεσμα.
- **Undo delete**: κράτησε τον διεγραμμένο χρήστη (με τη θέση του) σε μεταβλητή, δείξε μήνυμα με
  κουμπί «Αναίρεση» για μερικά δευτερόλεπτα, και επαναφέρον τον στη σωστή θέση (index, όχι append).
